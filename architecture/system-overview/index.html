    System Architecture Overview

    This document provides a high-level overview of the Nolain OCR system architecture, showing how all components interact.

    Component Layers

    1. Client Layer

    • Web Browser: User interface accessed via standard web browsers
    • Supports all modern browsers (Chrome, Firefox, Safari, Edge)

    2. Reverse Proxy Layer

    • Nginx: Entry point for all HTTP/HTTPS traffic
    • Routes / to Frontend (React SPA)
    • Routes /api/* to Backend (strips /api prefix)
    • Routes /webhook directly to Backend (Stripe webhooks)
    • Routes /health to Backend health check
    • Handles SSL/TLS termination in production
    • Security headers (HSTS, X-Frame-Options, etc.)
    • Request size limits (50MB local, 100MB production)
    • Forwards auth headers (X-User-ID, X-Access-Token)

    3. Frontend Layer

    • React SPA: Single-page application built with Vite
    • TypeScript for type safety
    • Tailwind CSS for styling
    • Radix UI for component primitives
    • TanStack Router for routing, TanStack Query for server state
    • Zustand Stores: Client-side state management
    • Auth store (user session)
    • Dashboard store (upload/extraction state)
    • Request store (API timing metrics)
    • Free Tools: 14 browser-only utilities (PDF merge/split, image tools, etc.) — no backend calls
    • Blog: Static markdown posts with build-time sitemap and prerendering
    • Solution Pages: Vertical marketing pages (invoices, receipts, insurance, etc.)

    4. Backend Layer

    • FastAPI: Python web framework
    • REST API endpoints (no /api/v1 prefix — nginx adds /api externally)
    • Server-Sent Events (SSE) at /stream/{task_id} for real-time extraction progress
    • Session auth via X-Access-Token (Supabase JWT) or X-User-Id headers

    • Pydantic schemas for validation

    • Celery Worker: Asynchronous task processor

    • Multi-image document extraction
    • Mistral AI batch processing for large jobs (≥50 images)
    • Page billing after completion

    5. Message Queue Layer

    • Redis: In-memory data store
    • Celery broker (task queue)
    • Celery result backend (task status)
    • Pub/Sub for real-time progress updates (task_updates:{task_id})

    6. External Services Layer

    • Supabase: Backend-as-a-Service
    • PostgreSQL database (subscriptions, user_sessions, topup_credit_purchases)

    • User authentication (email/password + Google OAuth)

    • Mistral AI: AI/ML Service

    • Vision model for OCR (mistral-small-latest by default)
    • Batch API for parallel processing of large jobs

    • JSON-structured extraction

    • Stripe: Payment Processing

    • Recurring subscriptions (Pro, Pro Plus)
    • One-time top-up page packs ($2 / $5 / $10 / $15)
    • Customer Portal and webhooks

    7. File Storage Layer

    • Local Filesystem: Temporary document storage
    • User uploads stored in backend/data/upload_{user_id}_{timestamp}/
    • PDF to image conversions (Poppler/pdf2image)
    • Cleaned up on logout

    Data Flow Patterns

    Pattern 1: User Authentication

    Browser → Nginx → React → FastAPI → Supabase Auth → FastAPI → React → Browser

    Google OAuth: Browser → Supabase OAuth → /auth/callback → POST /auth/session → authStore

    Pattern 2: Synchronous Document Upload

    Browser → Nginx → React → FastAPI → Local FS → Supabase (user_sessions) → React → Browser

    Pattern 3: Asynchronous OCR Extraction

    Browser → React → FastAPI → Redis (queue task) → returns task_id
                    ↓
          Celery Worker → Mistral AI → bill pages → Supabase
                    ↓
          Redis (publish progress) → FastAPI (SSE /stream) → React → Browser

    Pattern 4: Subscription & Top-up Management

    Browser → React → FastAPI → Stripe → Webhook → FastAPI → Supabase

    Deployment Architectures

    Local Development (Docker Compose)

    All services run in Docker containers on localhost: - Nginx: :80 - Frontend: :80 (internal) - Backend: :8000 (internal) - Redis: :6379 - Celery Worker: (no exposed port)

    Use nginx/nginx-local.conf or nginx/nginx.conf for local routing.

    Production (VPS)

    All services run in Docker containers on VPS: - Nginx: :80 (HTTP) + :443 (HTTPS) - Frontend: :80 (internal, served by Nginx) - Backend: :8000 (internal, proxied by Nginx) - Redis: :6379 (internal only) - Celery Worker: (no exposed port) - SSL certificates via Let's Encrypt (certbot/)

    Use nginx/nginx-production.conf for production routing.

    Key Design Decisions

    1. Nginx as Reverse Proxy: Single entry point, SSL termination, /api prefix stripping
    2. Async Processing: Multi-image extraction runs in Celery; returns task_id immediately
    3. Real-time Updates: SSE at /stream/{task_id} provides live progress without polling
    4. Session Auth: Supabase JWT via headers, not API keys
    5. Dual Billing Pools: Monthly plan quota consumed first, then top-up credits
    6. File Cleanup: Temporary files removed on logout to save disk space
    7. Page Limit Gating: Limits enforced at upload and billing time

    Scalability Considerations

    Current Architecture Supports:

    • Concurrent Users: ~100-500 (single VPS)
    • Document Processing: Async via Celery (no request timeout)
    • State: Redis in-memory (fast but volatile)
    • Storage: Local filesystem (VPS disk size)

    Scale Bottlenecks:

    1. Redis: Single instance, in-memory only
    2. Local Files: Limited by VPS disk space
    3. Celery Worker: Single worker process
    4. Mistral AI: Rate limits apply

    For scaling beyond current limits, see Alternatives - Async Processing and Assumptions - Traffic and Scaling.
