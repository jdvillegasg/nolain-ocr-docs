    Design choices

    Earlier chapters stated how the system behaves. This chapter names the bets that make that behavior look inevitable — and where those bets stop applying. It is not a catalog of libraries.

    If you want the layer map first, start with How nolainocr is built.

    Same layout, not mixed piles

    The product assumes a batch is one template. That yields aligned columns and an honest failure mode: split the folder. A classifier that sorts mixed documents in one upload would be a different product, with different errors and a different price.

    Consequence: users are asked to prepare the stack (including the free tools when a PDF is the wrong shape). The engine is not asked to be a mailroom.

    Session files, not a document CMS

    Keeping uploads only for the session reduces retention and disk. It also means nolainocr is a processor, not a filing cabinet. Logout is a delete. If you need history, you export.

    A saved-project library existed in earlier thinking and is not the current dashboard. Do not expect named archives to reappear without a product change.

    Hosted vision, not classical OCR alone

    Field extraction is done with a hosted vision model that returns structured data, not with a local character engine that only dumps text. The gain is semantics and tables; the cost is vendor dependence and per-page spend. Settlement charges pages because that is the unit the model (and the user) actually consume.

    Semantic columns, not exact labels

    Once the schema exists, later pages are allowed to use different words for the same box. The table stays usable in Excel. The failure mode is occasional over-merge. Exact string matching would produce cleaner uniqueness and worse spreadsheets.

    Background jobs for stacks, immediate return for one page

    A single image can finish while you wait. A stack cannot rely on one browser request. Progress on the dashboard is therefore part of the architecture, not decoration. Closing the tab early can mean you miss the result even if the job still finishes on the server — stay until the grid fills, then export.

    Pages and plans, not seats

    Pricing is built around pages per document and pages per month, plus optional overflow packs. That matches invoice-heavy months better than per-seat SaaS. It also makes the free tier a real trial: a short PDF fits; a two-hundred-page statement does not.

    Live numbers stay on nolainocr.com so this book does not drift from the catalog.

    Browser tools stay local

    Merge, split, and image utilities run in the browser so they can be free, logged-out, and off the extraction bill. They are adjacent product, not a back door into orchestration.

    Where this model stops

    • Unstructured essays, photos with no form, and mixed mail need a different pipeline.
    • Organizations that must keep a server-side archive need a different retention policy than logout-deletes-files.
    • Teams that need an API rather than a dashboard are outside this public book; contact is the path for custom work.

    Maintainer alternatives (other queues, databases, or OCR vendors) live in the private book (docs-private/) because they name implementations.
