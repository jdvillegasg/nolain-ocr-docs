    A job from start to finish

    The previous chapter named the parts. This chapter follows one realistic batch through them: a twelve-page PDF of same-layout invoices, two pages each, exported to Excel.

    If you have not read The parts of the system, start there. This is not a click-by-click tutorial; that is Extract your first documents.

    The scene

    You are signed in, email verified, on a plan that allows a twelve-page file. The PDF contains six invoices, two pages each, all from the same template. You want one spreadsheet.

    1. Upload

    The dashboard sends the PDF to orchestration. Orchestration checks file type and page count against the plan, converts each PDF page into an image the extractor can read, and stores those images in the session. The website shows previews.

    Nothing has been billed yet. You could log out and the files would be deleted.

    2. Configure the repeating unit

    You set pages per document to 2. That template group tells extraction to treat pages 1–2 as invoice A, 3–4 as invoice B, and so on. Leaving the control at 1 would have produced twelve thin records instead of six documents.

    This is still orchestration: it is a parameter on the job, not a new product.

    3. Start the job

    Choosing Extract Data admits the work. For more than one image the engine runs in the background. The website opens a progress channel and draws a bar. You keep the dashboard available so results can arrive.

    Settlement is consulted here only as a gate: if quota and top-ups are already empty, the job is refused before pixels reach the vision model.

    4. Schema from the first document

    The extraction layer reads the first group (pages 1–2) and proposes field names — invoice number, date, vendor, lines, totals. That list is the schema for the rest of the PDF.

    If the first document is a cover sheet with a different layout from the invoices, the schema will be wrong for the stack. That is a preparation mistake, not a hidden setting: put a representative page first, or split the file.

    5. Remaining pages

    Later groups are read into the same columns. Nested objects become flat names (vendor + name → a vendor-name column). Labels that mean the same thing are aligned so the sixth invoice does not create a private extra column for “Inv. #”.

    Large stacks may spend longer in this stage; progress ticks as groups complete.

    6. Settle pages

    When the table is ready, settlement counts the pages that were processed and subtracts them from monthly quota, then from top-up pages if needed. The account screen’s usage number moves.

    If the job fails before completion, treat the usage figure on Account as the source of truth for whether pages were charged. The product intends to bill completed extraction.

    7. See and export

    The results grid fills. You download Excel. That file is now on your computer. Logging out deletes the session images; it does not retract the spreadsheet.

    Other journeys, same skeleton

    Journey What changes What does not
    Single image No background job; the table returns on the same request Schema, session, page billing
    Many one-page receipts Template group stays 1 Same-layout rule
    Sign-up then first extract Identity and a free plan record are created first Extraction still session-scoped
    Hit a limit Orchestration refuses at the gate You change plan or top up, then retry
    Logout Session files go away Plan and usage remain

    Password reset, Google sign-in, and Stripe checkout are settlement side-quests. They are specified in Accounts and access and Billing and pages, not in this pipeline.

    Where a job can stop

    • Before upload: wrong file type, too many pages for the plan.
    • Before extraction: no remaining pages.
    • During extraction: provider or job-queue failure; retry, then contact support with the time and the on-screen error.
    • After extraction: export is a client action; an empty grid means the job did not actually complete.

    User-facing recovery is in Troubleshooting.
